# Insta360 视障辅助项目宪章 (Constitution)

## 核心原则 (Core Principles)

### 原则一：项目背景
**定位**：本项目是利用insta360的DAP模型开发视障者辅助工具的insta360黑客松比赛项目。  
**架构**：项目主要有DAP模型后端、连接insta x5 全景相机视频流管道、客户端组成。后端推理首选在ios，其次是mac。

### 原则二：极致低延迟
根据项目目标用户，需要对系统架构进行极致优化，确保视频流解析、图像分析和语音、音频反馈等流程的端到端延迟控制在极低范围内，满足视障用户对于实时环境感知的核心诉求。

### 原则四：绝对无障碍适配（最高底线要求）
交互设计必须全面且深刻地考虑视障者的使用习惯。在实现 UI 时，无障碍适配是第一优先事务，**绝对禁止** AI 回复中出现对视障者的偏见或不适宜用语。在 UI 层必须严格遵守以下 7 项基本原则及无障碍双轨定律：
1. **点击操作**：所有可点击的 widget 必须响应屏幕阅读器标准的激活 widget 操作。
2. **标签规范**：
   - a. 所有采用图标样式的可交互 widget 必须有简洁易懂的文本标签（原则是使用单词或者短语，如用“设置”代替“打开设置界面”）。
   - b. 对于具有上下文关联的组件（如左侧是歌曲名称，右侧是该歌曲的播放按钮），按钮的标签必须采用“标签，上下文”的统一格式。
   - c. 如果 widget 原本就有文本字段（例如大多数技术栈的 button 不需要额外的 a11y 接口就满足），则优先使用 widget 的原生能力，直接使用其原生无障碍属性声明（如 `Text.semanticsLabel`、`Icon.semanticLabel`），**绝对禁止**在其外层嵌套多余的 `Semantics` 包装，从源头杜绝双重聚焦（“原生内聚”原则）。
3. **额外提示**：如果标签不足以传达信息时，可以在 widget 的专用说明字段中提供补充说明信息（如 hint 字段）。
4. **焦点控制**：
   - a. 所有可交互 widget、有意义的内容必须能被屏幕阅读器聚焦；所有纯装饰性元素应该对屏幕阅读器隐藏。
   - b. 如果可交互 widget 是复合组件中的一部分，可采用适配屏幕阅读器自定义操作（iOS 的转子），也可采用标签原则中的 b。如果采用前者，则该 widget 本身必须对屏幕阅读器隐藏，避免焦点碎片化。
   - c. **合并与阻断规则**：当将多个散落的子文本合并为一个复合卡片组件进行整体聚焦时，必须在外层建立独立的语义容器。合并后的语义必须根据语言环境使用**中文或英文逗号**进行平铺拼接，防止焦点碎片化与读屏高亮噪点（“边界阻断”原则）。
5. **对比度要求**：widget 或文本与背景之间的对比度至少为 4.5:1（禁用组件除外）。
6. **避免内容自动刷新**：避免用户在操作时（或操作未结束时）触发界面自动刷新（典型例子是渐进式搜索导致焦点跳动丢失），除非该具体功能提供了特有的无障碍反馈机制。
7. **可点击目标大小**：所有可点击目标的尺寸应至少为 48x48 像素。

**本原则的核心是使用 iOS 提供的默认 UI 组件绝对不会犯错。**

### 原则五：严格统一的中文语言规范
本项目的所有产物（包括但不限于：功能规范 Spec、技术计划 Plan、任务拆解 Tasks、代码注释、系统文档以及所有 AI 的回复文案）必须**统一、严格地使用中文**。
- **代码标识符**：类名、方法名、变量名等代码标识符**必须使用英文，且遵循行业缩写习惯**，遵循编程语言通用规范。
- **注释规范**：代码注释必须简洁清晰易懂，**严禁**出现中英文混杂或默认生成英文注释的情况。
- **注释位置**：代码注释必须先于代码，即在所有核心业务逻辑前，必须有简洁清晰的注释说明逻辑意图。

### 原则六：Git 提交规范
为了保证代码库的可追溯性与清晰度，必须严格遵守以下版本控制规范：
- **纯中文提交**：每次 Git 的提交消息（Commit Message）必须使用**纯中文**撰写，简明扼要地说明变更意图。
- **任务粒度提交**：每完成一个阶段（经本地单元测试通过后），**必须立即执行一次 Git 提交**，避免在开发结束时进行大颗粒度的杂糅提交。

### 原则七：依赖库使用与引入规范
1. **使用规范**：调用项目引入的依赖库时，必须查阅官方文档。必须严格根据文档指引来使用依赖库，绝对不可以凭空捏造 API。
2. **引入规范**：引入任何第三方依赖前，必须深思熟虑。若能使用标准库或项目内现有库实现，则严禁引入新依赖。引入前必须评估依赖项的维护状态、社区活跃度及包体积，且必须显式向用户解释原因，严禁隐蔽修改配置文件。

### 原则八：日志语言规范
为了保证排障效率与全流程的语言一致性，我们程序自身产生的**所有业务日志内容必须使用中文**。这包括核心报错信息、业务上下文提示等字段值。对于结构化与机器可读日志中的日志级别标识（Level/lvl），直接遵循行业通用标准（如 `DEBUG`、`INFO`、`WARNING`、`ERROR`、`SEVERE`），无需强行翻译为中文，以兼顾通用 AI 与自动化脚本的高效解析。**依赖库所产生的内部日志内容保持原样**，不得强行翻译或篡改，以免丢失原始错误上下文。

### 原则九：统一业务日志埋点规范
为了实现全链路可观测性并确保线上故障的快速定位，所有业务流程必须集成统一日志埋点。
1. **强制性埋点**：所有核心业务流（如状态切换、设备连接、关键决策、错误处理点）必须包含结构化日志记录。
2. **结构化调用**：前端必须通过标准的 Swift `Log` 工具进行记录，严禁在业务代码中使用 `print()` 进行调试输出。
3. **语言规范与行业标准**：日志级别（Level/lvl）直接采用行业标准英文枚举（`DEBUG`、`INFO`、`WARNING`、`ERROR`、`SEVERE`），不强行汉化；而业务消息内容（Message/msg）遵循全中文规范。

### 原则十：健壮性验证与质量门禁 (Quality Gates)
1. **严禁孤岛化验证**：单文件或局部单元测试的通过不代表全项目的可交付性。在涉及第三方库更新或跨模块服务改动后，严禁仅凭局部测试结果判定任务完成。
2. **强制性全量静态分析**：凡是修改了依赖配置文件或调整了核心服务契约，**必须**在提交前运行一次全项目的静态分析指令。
3. **逻辑与编译双成功原则**：一个任务的完成标准必须同时满足“业务逻辑测试通过”且“全项目静态检查无误（Zero Errors）”。

### 原则十一：写前必读与编前思考 (Read & Think Before Action)
1. **写前必读 (Read Before You Write)**：
   - 编写任何代码前，**必须**完整阅读将要修改的文件，而不是粗略浏览。
   - **必须**观察并严格遵循项目中类似功能的既有模式（如 API 路由、命名规范、目录结构）。
   - **必须**检查文件顶部的导入（Imports），使用项目已有的库，严禁盲目引入新依赖。
   - **必须**查阅相关的测试文件以明确预期的真实行为，而非凭空猜测。
   - 若对项目内既有模式存在疑问，**必须**主动提出，严禁凭经验盲目猜测。
2. **编前思考 (Think Before You Code)**：
   - 开始编码前，**必须**理清思路并陈述设计假设，绝不在沉默中做出关键决策。
   - **必须**明确阐述所选方案的利弊与权衡（Tradeoffs），让审查者知晓其复杂性成本。
   - 若存在多种实现方案，**必须**简要列出 2 至 3 种候选方案，并给出明确的推荐与理由。
   - 遇到任何需求冲突或概念混淆时，**必须**立即停止编码进行澄清，决不能用看起来合理但实际上错误的代码填补空白。

### 原则十二：极致简朴与外科手术式修改 (Simplicity & Surgical Changes)
1. **极致简朴 (Simplicity & YAGNI)**：
   - **必须**编写能解决当前具体问题的最少代码。严禁编写“为了未来扩展”的无用抽象。
   - **严禁过度设计**：
     - **杜绝过早抽象**：对于单一使用场景，必须直接编写具体实现函数，严禁引入复杂的策略模式等。
     - **杜绝投机性错误处理**：不为理论上不可能发生的错误编写复杂的捕获与验证逻辑。
     - **杜绝不必要的配置化**：不为不会更改的参数提供配置文件、环境变量或参数项，直接硬编码。
     - **杜绝无实际效益的灵活性**：不编写只有单一实现类的接口、抽象基类或泛型。
2. **外科手术式精确变更 (Surgical Changes)**：
   - 代码变更差分（Diff）**必须**保持最小化，绝不触碰与当前任务无关的任何代码。
   - **必须**遵循目标文件已有的代码风格（如单/双引号、命名风格、分号规则等），一致性高于个人喜好。
   - **必须**清理且仅清理因自己本次变更产生的死代码（如未使用的导入、变量或函数），不清理历史遗留死代码。
   - **严禁全盘格式化**：除非用户明确要求，否则禁止对整个文件运行格式化工具或进行大规模缩进调整，防止污染 Git Diff 历史。

### 原则十三：调试验证与测试先行 (Debugging & Verification)
1. **调试与排障 (Debugging)**：
   - 遇到错误时，**必须**完整阅读错误信息及堆栈轨迹（Stack Trace），严禁根据错误类型臆造修复方案。
   - 修改代码前，**必须**先稳定复现问题，严禁在无法验证的情况下猜测性地修改代码。
   - 调试时，**必须**遵循“单变量控制”，一次仅修改一个地方并进行测试。
   - **严禁权宜之计**：如果某个值非预期为 null，必须彻底查明其为 null 的根本原因并予以解决，严禁仅添加一个空值检查来掩盖潜在隐患。
   - 调试陷入瓶颈时，**必须**主动向用户反馈并说明已尝试的路径，绝不陷入盲目尝试的无限循环。
2. **验证与测试 (Verification)**：
   - 修复 Bug 时，**必须**测试先行：先编写能复现 Bug 的测试用例，运行并确认失败，修复后再确保该测试通过。
   - 修改代码后，**必须**运行现有的测试套件，绝不让新的修改破坏既有功能。
   - 测试应关注业务行为与接口契约，而非代码的琐碎实现细节。
   - 若受客观架构限制导致无法编写自动化测试，**必须**显式说明原因，并列出替代的手工验证步骤。

### 原则十四：透明沟通与精准反馈 (Transparent Communication)
1. **专业且透明的沟通**：
   - **必须**清晰总结做出的修改及其背后的技术考量，不倾倒无解释的代码块。
   - 评估出实现方案有潜在隐患（如在大列表循环中进行数据库查询）时，**必须**主动提出关切并给出优化建议。
   - 对于不确定的领域，**必须**精确指出盲区，绝不用模糊的假设敷衍。
   - 沟通内容**必须**符合受众上下文，不向专业开发者赘述计算机常识，保持沟通的高效专业。
2. **Git 提交信息**：
   - Git 提交信息（Commit Message）**必须**具体清晰，准确描述变更的具体模块和解决的核心问题。

### 原则十五：常见避坑指南与失效防范 (Avoid Common Failure Modes)
在日常开发中，**必须**时刻警惕并绝对避免以下 7 种 LLM 常见失效模式：
1. **大杂烩式修改 (Kitchen Sink)**：偏离主要任务，在修复 A 时顺手重构半个代码库。
2. **错误的抽象 (Wrong Abstraction)**：为仅有一两处使用的场景设计过度通用、复杂的逻辑。重复两次的代码比错误的抽象成本更低。
3. **隐蔽的决策 (Invisible Decision)**：在没有提示用户的情况下，擅自选定数据库 Schema、API 契约或安全策略等关键架构设计。
4. **理想路径幻觉 (Optimistic Path)**：只编写符合预期流向的“快乐路径”代码，忽略或在遇到接口 500、文件不存在、网络异常或非法输入时发生崩溃。
5. **知识幻觉 (Knowledge Hallucination)**：凭空创造不存在的 API、方法签名或已在当前版本废弃的参数。使用任何不确定的库函数前必须查阅文档或源码。
6. **风格漂移 (Style Drift)**：在 OOP 架构中写函数式，或在 TS 项目中引入 JS 写法，破坏整体项目的风格一致性。
7. **失控的重构 (Runaway Refactor)**：在修复一个问题的过程中，因连锁反应导致修改的文件数量呈指数级增加。一旦发现重构范围失控，必须立即停止并与用户同步。

## 架构与代码组织规范

必须严格遵循跨平台及 Monorepo 最佳实践。前后端需建立清晰的接口契约（API Contracts），并在设计时将性能与无障碍兼容性作为架构审核的关键指标。

## 开发与审查流程

所有新功能规划（Plan）、功能规范（Spec）及任务拆解（Tasks）必须经过宪章核查（Constitution Check）。任何不符合“极致安全性”、“低延迟”或“无障碍适配”底线要求的提案将被一票否决。所有文档、规划和代码注释在审查时必须确保完全使用中文。

## 治理 (Governance)

所有提交的代码和文档均须经过此宪章各项原则的严格核查。在规划、设计和开发中，任何违反安全性或无障碍规范的设计都将被直接驳回。对宪章的任何修改需要提交专门的文档说明并更新版本号。
